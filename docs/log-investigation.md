# Offline log investigation

Investigate supplied Windows event records without a paid AI API. The browser
workspace and Python CLI apply three deterministic candidate rules. Neither
collects records automatically, confirms an attack, executes commands, or
identifies the person behind a VPN or shared address.

## Start with synthetic data

Use the labelled **suspicious** and **benign** examples in the log workspace.
They describe no real account, host or incident. The suspicious example produces
R001, R002 and R003; the benign example produces no matches. A clean result from
three rules is not a security assessment.

The matching CLI files are in `tools/loglab/fixtures/`. Use these examples before
importing any authorized private records.

## Browser versus CLI

- **Browser:** analyzes one supplied dataset in memory. Replacing it replaces
  the current investigation. Reloading or clearing it removes the in-memory
  records. The importer sends no records to the backend, an AI provider or public
  feeds. The rest of the dashboard still makes its documented public-feed
  requests; this does not make the entire web page network-free.
- **Python CLI:** retains normalized records and provenance in an explicit local
  SQLite file. It runs without Node.js, a web server, packages, API keys or network
  access. Redacted reports are generated locally. Closing it does not delete the
  database or imported files.

The browser accepts JSON, NDJSON, CSV and plain Windows event XML. The CLI accepts
canonical JSON, NDJSON/JSONL and CSV; it does not import EVTX or XML directly.
Use the optional exporter below to create canonical JSON from authorized local
Windows channels. No Sysmon installation or service is included in this project.

## Python and SQLite workflow

Requires an installed **Python 3.12 or later**. Run from the repository root.
`python --version` should identify the interpreter, not a Microsoft Store alias.
If needed, substitute your installed interpreter command, such as `py -3.12`
on Windows or `python3` on another system. No `pip install` is needed.

These commands use synthetic records only:

```powershell
python -m tools.loglab --db logs/private-loglab.sqlite init
python -m tools.loglab --db logs/private-loglab.sqlite import tools/loglab/fixtures/suspicious.synthetic.json
python -m tools.loglab --db logs/private-loglab.sqlite analyze
python -m tools.loglab --db logs/private-loglab.sqlite report --output logs/redacted-investigation.md
```

`import` also initializes a new compatible database. It prints inserted,
duplicate, unsupported and missing-identity/process counts. Missing identity
excludes a record from authentication correlation; missing executable or command
line prevents a process-creation match. `analyze` prints the run identifier and
candidate count. `report --run <run-id>` selects a retained analysis; otherwise
the latest is used. Reports require a new output filename and never overwrite an
existing file.

For another supported file extension, `import <file> --format csv` (or `json`,
`ndjson`, `jsonl`) selects the format explicitly.

Imports are capped at **5 MiB UTF-8** and **10,000 raw records**, including
duplicates and unsupported events. Validation happens before any records are
written. JSON nesting is limited to 64 levels. A malformed record rejects the complete import; a well-formed
unsupported event type is counted and skipped. SQLite retains at most **10,000
unique supported records across imports**. If an import would exceed this
capacity, the import and its provenance roll back. Use a separate private database
for another investigation rather than mixing unrelated cases.

SQLite contains `events`, `imports`, `event_imports`, `analysis_runs`, `alerts`,
`alert_evidence` and `run_alerts`. Imports retain the source-file SHA-256 and
supported-record row numbers/original IDs. Equivalent normalized events deduplicate
even if their supplied IDs differ. Analysis retains explicit alert-to-evidence
relations. Stable FNV identifiers are lookup keys, **not cryptographic proof of
authenticity**. The source hash fingerprints the supplied file; it does not prove
the file was generated by a trusted system.

`tools/loglab/sql/analysis.sql` has read-only queries for event coverage,
authentication outcomes, evidence timelines, provenance and five-minute failure
density. Query outputs contain private identities. The SQL density query is
exploratory; exact boundary decisions use the tested millisecond rule engines.

## Canonical format

JSON is an array; NDJSON is one object per non-empty line. Canonical CSV needs
the `timestamp`, `host`, `channel` and `eventId` headers. Optional columns use the
same field names below. The browser also recognizes common Windows CSV aliases;
the CLI intentionally uses canonical headers.

```json
[
  {
    "id": "synthetic-record-001",
    "timestamp": "2026-10-09T09:00:00.000Z",
    "host": "SYNTHETIC-LAB-01",
    "channel": "Security",
    "eventId": 4625,
    "user": "synthetic-user",
    "sourceIp": "192.0.2.42",
    "process": "",
    "commandLine": ""
  }
]
```

- `timestamp`: a real ISO calendar date-time with `Z` or an explicit numeric
  timezone. Normalized to UTC milliseconds; finer precision is truncated.
- `host`: required non-empty text, at most 256 UTF-8 bytes.
- `channel`: `Security` or `Sysmon`. The full
  `Microsoft-Windows-Sysmon/Operational` name also normalizes to `Sysmon`.
  Channel names are bounded to 128 UTF-8 bytes and cannot contain control characters.
- `eventId`: a positive safe integer number in JSON, or digits in CSV.
- `user`, `sourceIp`, `process`, `commandLine`: optional text; missing/null values
  and a Windows `-` placeholder become empty strings. Byte limits are respectively
  256, 128, 1,024 and 8,192. Unsupported control characters are rejected.
- `id`: optional untrusted source metadata, not the deduplication identity.
  The CLI can retain a bounded original string in private import provenance.
  Unknown additional fields are discarded rather than stored or analyzed.

Supported records are **Security 4624/4625** and **Sysmon 1/3**. Sysmon 3 is
context only: this narrow schema retains its recorded source address and process,
not destination addresses or ports, and no network rule runs on it. A Sysmon
network source address can belong to the observed local host, not an attacker.

## Candidate rules and limits

- **R001, repeated failed logons:** five Security 4625 events with exactly the
  same host, user and recorded source IP within an inclusive five-minute window.
  One match per contiguous failure burst; a gap longer than five minutes starts
  another burst. Evidence is the first qualifying five-record proof.
- **R002, successful logon after failures:** a same-identity Security 4624 event
  strictly after a qualifying five-failure window, within ten minutes of its
  final failure. One match per success uses the latest eligible five failures.
  Equal-timestamp success/failure ordering is not assumed.
- **R003, encoded PowerShell command:** Sysmon 1 identifies `powershell` or
  `pwsh`, with or without `.exe`, and a literal `-enc` or `-encodedcommand`
  argument, ignoring case. Quoted arguments are tokenized; text after `-Command`
  or `-File` is not treated as launch switches. An unmatched quote does not match.
  Encoded content is never decoded or executed.

Identity strings match exactly after trimming. No alias resolution, Windows
account case-folding, IP enrichment, geolocation or attribution is performed.
Missing users/source IPs do not correlate. The rules do not model every logon
type, distinguish every administrative action, cover alternate PowerShell
switch abbreviations/evasion, or detect all attacks. Password retries and
legitimate automation can match. Review original context before escalating.

## Optional authorized Windows export

The script is **manual and opt-in**. It reads local channels only, never installs
Sysmon, changes auditing, creates a service, schedules collection or requests
elevation. Start with an account already authorized to read the requested logs.
If access is denied or a requested channel is absent, it fails without writing an
export. Do not bypass access controls to obtain records.

Create a private local output directory first. Supply a **new absolute `.json`
filename** and explicit-timezone start/end values spanning at most seven days:

```powershell
.\scripts\export-windows-logs.ps1 `
  -OutputPath 'C:\PrivateLogs\authorized-events.json' `
  -StartTime '2026-10-09T09:00:00Z' `
  -EndTime '2026-10-09T10:00:00Z' `
  -MaxRecords 1000
```

Only Security 4624/4625 are requested by default. Add `-IncludeSysmon` to include
Sysmon 1/3 **if Sysmon is already installed, configured and accessible**. The
exporter reads named XML EventData fields, not version-dependent positional
indexes. It rejects a result over the selected count (maximum 10,000) or 5 MiB
rather than silently exporting an incomplete set. It does not run during app
startup or tests. This implementation was tested with mocked synthetic records;
the manual exporter was not used to collect private Windows logs for its
verification. The separate opt-in endpoint collector has its own documented
local checks; it is not this file-export workflow.

## Privacy and report handling

**The SQLite database and source export remain sensitive even when a report is
redacted.** They can contain usernames, addresses, command lines and secrets.
Keep them outside version control and public/synced storage, use appropriate
filesystem permissions/encryption, and follow your retention policy. The `logs/`
directory is ignored by Git in this project; choosing another path does not
automatically make it safe to publish.

CLI reports pseudonymize host/user/IP values using a per-database random HMAC
key, omit command lines, process paths, original record identifiers and filenames,
and use local evidence labels. Browser exports also mask identity fields and
omit commands. Exact timestamps and behavioral patterns remain identifying;
these are **pseudonymized, not anonymous**, reports. Review every export before
sharing. There is no automatic containment or action on accounts.
